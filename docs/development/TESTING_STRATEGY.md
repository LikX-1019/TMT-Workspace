# Testing Strategy

## Goals

The test suite is the executable contract of the platform. It must give future contributors confidence that identity, organization, workspace navigation, permissions, data scope, and audit do not silently regress.

Speed and precision matter: unit tests should isolate rules, while API tests should prove the composed dependency graph and response contract.

## Test Layers

### Unit tests

Cover:

- pure service rules;
- configuration edge cases;
- permission/scope policy logic;
- serialization/validation rules;
- date, sorting, tree, and pagination helpers.

They should not require HTTP or PostgreSQL unless specifically testing database expressions.

### API contract tests

Use FastAPI's ASGI transport to verify:

- route/status codes;
- success/error envelope;
- request validation;
- authentication/authorization dependencies;
- response schema;
- pagination metadata.

### Database integration tests

Use isolated PostgreSQL test databases for:

- ORM mapping and constraints;
- unique/partial indexes;
- foreign keys;
- department recursive-subtree queries and cycle prevention;
- repository filters;
- migration upgrade/downgrade where practical.

Current Phase 0 uses a lightweight SQLite override for the readiness endpoint contract. Once entity tables and PostgreSQL-specific constraints exist, repository and migration tests must run against PostgreSQL.

### Permission tests

Every protected feature must have both positive and negative tests. The suite must prove denial, not merely check that a valid administrator succeeds.

### Audit tests

For sensitive operations, assert that required evidence is written with masked sensitive fields and that unauthorized attempts do not fabricate successful audit outcomes.

## Test Layout

```text
tests/
  conftest.py
  test_health_api.py
  test_response_conventions.py
  modules/
    auth/
    users/
    departments/
    roles/
    workspaces/
    announcements/
    audit/
```

Mirror module behavior under `tests/modules/<module>/` once Phase 1 begins.

## Fixtures

Common fixtures should provide:

- application with dependency overrides;
- isolated database session/transaction;
- normal user, department operator, workspace operator, system administrator, and security auditor;
- active/disabled/resigned users;
- three-level department tree;
- workspace with directory/page/action menus;
- role sets with different data scopes.

Fixture data should state the scenario in its name or factory function, for example `department_operator_in_child_department`.

## Core Permission Matrix

The test matrix must include at least:

| Actor | Attempt | Expected |
| --- | --- | --- |
| Anonymous | Access protected API | `401` |
| Disabled account | Valid token/API access | denied |
| Resigned user | Login/API access | denied |
| User without action permission | Protected API | `403` |
| User with action permission but wrong workspace | Workspace API | denied |
| Department operator | Row in another department | denied/hidden |
| Department operator | Row in descendant department | allowed |
| Self-scope user | Another user's row | denied/hidden |
| `ALL` scope operator | Allowed operation | allowed and audited |

Do not encode this only as a documentation table. Each security-critical feature adds executable cases.

## RBAC Test Scenarios

1. Role permission union grants access from any qualifying role.
2. Removing the only qualifying role removes access on the next request.
3. Disabling a role/user removes effective access.
4. Direct use of a valid menu code without backend permission fails.
5. Position assignment alone never grants permission.
6. Sensitive role changes are audited.

## Data Scope Test Scenarios

1. `DEPARTMENT` sees own department, not sibling.
2. `DEPARTMENT_AND_CHILDREN` sees descendants, not siblings.
3. `SELF` sees owned/assigned rows only.
4. `CUSTOM` sees only explicitly assigned departments.
5. Missing department context sees no department-scoped rows.
6. Mutation fetch/update enforces the same predicate as read.

## API Error Tests

Assert exact machine-readable code and status for:

- malformed UUID;
- invalid enum;
- invalid pagination bound;
- duplicate stable code;
- forbidden operation;
- unauthenticated request;
- out-of-scope object.

Do not assert internal stack traces.

## Migration Tests

Database migration standards:

- initial migration creates all documented constraints/indexes.
- autogenerated revisions are reviewed.
- destructive changes have a tested path.
- for PostgreSQL-specific behavior, run migration tests in CI against PostgreSQL.

## Test Data Rules

- No real employee/customer/secret data.
- Use deterministic factories over sprawling JSON fixtures.
- Unique values must not collide between tests.
- Time-dependent logic uses injectable clocks or freezegun-style control.
- Fixtures clean up after themselves or use transactional rollback.

## Coverage Policy

Coverage is a diagnostic, not a target. Initial expectation:

- core utilities and security dependencies: high confidence through direct tests;
- services/rules: covered including failure paths;
- API routes: contract tested;
- migrations/constraints: exercised.

No percentage excuses an untested permission path.

## CI Gate

Every change runs:

```bash
uv run ruff format --check .
uv run ruff check .
uv run mypy
uv run pytest
```

Database-specific CI should add PostgreSQL service containers before Phase 1 merges. Security-sensitive changes should be labeled/reviewed even when all automated tests pass.
